01 • Fundamentos

El Reto: Monolito Tradicional vs. Arquitectura Cloud Native

02 / 10

✖ Riesgos del Enfoque Tradicional

Gestión de Contraseñas Locales
Guardar hashes en BD propia expone al negocio a filtraciones críticas y ataques de fuerza bruta.
Acoplamiento y Sesiones en Memoria
Sesiones HTTP en el servidor impiden escalar horizontalmente sin réplicas complejas.
Punto Único de Falla (SPOF)
Si la base de datos o el servidor colapsan, todo el ecosistema cae sin aislamiento.

✔ Nuestra Solución: Cloud Native & Zero Trust

Identidad Delegada (IDaaS)
AWS Cognito asume el 100% de la responsabilidad de usuarios, passwords, MFA y tokens.
Arquitectura 100% Stateless (JWT)
El backend no almacena estados ni sesiones; cada petición valida asimétricamente su token.
Desacoplamiento Multi-Cloud Total
Servicios independientes en Vercel, AWS, Render y Supabase con máxima resiliencia.
02 • Arquitectura

Topología del Sistema: Ecosistema Multi-Cloud Desacoplado

03 / 10

1. Frontend SPA (Vercel) — React 19 + TypeScript + Vite

Aplicación estática de alto rendimiento. Acceso público al catálogo y orquestación de autenticación con PKCE.

Base de datos relacional administrada conectada mediante pool transaccional seguro (puerto 5432 HikariCP).

03 • Seguridad IDaaS

Gestión de Identidad: AWS Cognito y Protocolo PKCE

04 / 10

Cero Contraseñas Locales

• Nuestra aplicación ni el servidor ven jamás las contraseñas del usuario.

• Eliminamos el riesgo de filtraciones y cumplimos normativas internacionales.

• Auto-confirmación por correo con códigos seguros de 6 dígitos.

Hosted UI Oficial de AWS

• Interfaz de inicio de sesión alojada en la nube global de Amazon Web Services.

• Protección nativa contra ataques de fuerza bruta, bots y credenciales falsas.

• Aislamiento absoluto entre la interfaz del usuario y nuestro backend.

Flujo Criptográfico PKCE

• Proof Key for Code Exchange (RFC 7636) diseñado para clientes públicos SPA.

• Genera code_verifier y code_challenge al vuelo para evitar intercepciones.

• Garantiza que sólo quien solicitó el login pueda canjear los tokens JWT.

04 • Protección de Red

Defensa en Profundidad: Doble Filtro de Seguridad

05 / 10

🛡️ 1° Filtro: Perímetro (Amazon API Gateway)

Cognito Authorizer en el Borde
El Gateway intercepta la cabecera Authorization antes de reenviar el tráfico al servidor.
Bloqueo Inmediato (HTTP 401)
Peticiones con tokens vencidos o fraudulentos son rechazadas en el perímetro.
Ahorro de Cómputo y Resiliencia
El backend en Render nunca procesa tráfico malicioso, ahorrando memoria y CPU.

🔒 2° Filtro: Backend (Spring Security 6)

Resource Server Criptográfico
Spring Boot valida asimétricamente (RS256) la firma digital del token recibido.
Verificación con JWKS de AWS
Descarga claves públicas directas desde Amazon; sin contraseñas compartidas.
Extracción de Identidad Segura
Asocia cada acción al correo del claim 'email' garantizando autoría y no repudio.
05 • Criptografía JWT

Anatomía del Token JWT: El Pasaporte Digital

06 / 10

1. Header (Encabezado)

• Algoritmo: RS256 (Asimétrico)

• Tipo: JWT

• Key ID (kid): Identifica llave en JWKS

2. Payload (Claims)

• sub: UUID único del usuario

• email: Correo verificado

• iss: Emisor oficial Cognito

• exp: Expiración matemática

3. Signature (Firma Digital)

• Cifrado asimétrico con clave privada AWS

• Integridad matemática absoluta

• Si se altera un bit, la firma se anula

💡 Analogía: El JWT es como un pasaporte sellado por un consulado (AWS). El backend no necesita llamar al consulado en cada petición; sólo verifica que el sello sea auténtico usando la clave pública consular.

06 • Backend & Lógica

Backend Stateless: Spring Boot 3 & Resource Server

07 / 10

Arquitectura 100% Stateless

El backend no guarda sesiones en memoria ni cookies de sesión. Cada petición HTTP es autónoma y autosuficiente, permitiendo réplicas instantáneas en Render sin sincronización de caché.

Sincronización Automática con JWKS

Spring Security consulta el endpoint de llaves públicas de Cognito: valida emisor (iss), audiencia y vigencia temporal (exp) de forma asimétrica y automática sin escribir código de verificación manual.

Extracción de Identidad Segura

Mediante la anotación @AuthenticationPrincipal Jwt, el controlador obtiene directamente el email verificado del usuario para registrar la autoría del producto sin riesgo de suplantación.

07 • Almacenamiento

Persistencia Cloud: Supabase PostgreSQL Gestionado

08 / 10

Base de Datos Relacional ACID

PostgreSQL 15+ administrado en la nube con integridad transaccional, claves foráneas, índices optimizados y respaldos continuos sin mantenimiento manual de infraestructura.

Session Pooler (Puerto 5432)

Integración optimizada con HikariCP. El pooler de Supabase multiplexa las conexiones concurrentes, evitando la saturación del servidor bajo alta concurrencia o reinicios de instancias en Render.

Aislamiento Total de Credenciales

La base de datos sólo acepta conexiones SSL cifradas. Las credenciales residen en variables de entorno seguras en Render, jamás expuestas en el código fuente ni en el repositorio GitHub.

Demostración Práctica: Circuito de Validación en Vivo

09 / 10

Paso 1: Acceso Público

Ingreso a Vercel sin sesión activa. El catálogo de productos carga de forma pública desde Supabase sin restricciones.

Paso 2: Login con Cognito

Clic en 'Iniciar sesión'. Redirección segura a la Hosted UI oficial de AWS y validación criptográfica con PKCE.

Paso 3: Creación de Producto

Completar formulario. Petición POST protegida con cabecera Authorization: Bearer <token> hacia API Gateway.

Paso 4: Auditoría y Persistencia

El backend valida el token, guarda en Supabase (puerto 5432) y la interfaz de React se actualiza al instante.
